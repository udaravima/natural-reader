# v2.2 hardening: every piece of browser state belongs to its user

> Follows [2026-09-28-v2.1-follow-ups.md](2026-09-28-v2.1-follow-ups.md). Its final whole-branch review found that Task 4 made only "Your Library" per-user; three other stores in the browser are still shared by everyone who signs in on it. Two small correctness bugs found by the same review travel with this work.

**Goal:** On a shared browser, the next person to sign in sees nothing the previous person left behind, and a single-user install loses nothing on upgrade.

**Architecture:** No new subsystems. The ownership mechanism from v2.1 Task 4 (`src/db.js`: `currentOwnerId`, `setLibraryOwner(id, { claimLegacy })`, fail-closed when no owner is known) is extended to the other stores. Legacy (pre-release) data is claimed once, by the first user who signs in, in the same claim.

## Global constraints

Same as the v2.1 plan:
- Nothing deployment-specific is hardcoded.
- No user content at WARNING or above.
- Every task leaves `pytest`, `npx vitest run` (**exit code 0**, not just the pass count) and `npx eslint src` green.
- TDD.
- One CHANGELOG `[Unreleased]` line per user-visible change.

## Review focus

1. After user A signs out and B signs in on the same browser, B must not see A's browser-only chats or A's workspace folder, and must not resume A's reading positions.
2. When no user is known (before `/v1/auth/me`, after a 401, or when `/me` fails), nothing is read from or written to any of these stores.
3. A single-user install keeps its chats, workspace and reading positions after the upgrade: the first sign-in claims them.

---

### Task A: Browser-only chats, the workspace and reading positions belong to the signed-in user

**Why:** The final review of v2.1 found three stores that are still shared on one browser:
- **Browser-only chats:** `sessionStore.getRecentSessions` merges `idb.getRecentSessions()` for whoever is signed in.
- **The last workspace folder:** `App.jsx`'s restore effect re-opens it on mount, before the app even knows who is signed in.
- **Reading positions:** `localStorage` keys `neural-pdf-progress-<fileName>`.

**Change:**
- **`chat_sessions` (IndexedDB):**
  - Records get an `ownerId`, stamped by `saveSession`.
  - `getRecentSessions`, `getSession`, `saveSession` and `deleteSession` see only the current owner's records, and nothing when no owner is known.
  - Records with no `ownerId` are claimed by the claim in `setLibraryOwner(id, { claimLegacy: true })`.
  - Keys are unchanged (session ids are unique), so there is no version bump.
- **`workspaces` (IndexedDB):**
  - The single record `'last'` becomes one per owner, `last:<ownerId>`.
  - The legacy `'last'` record is claimed.
  - With no owner, reads return null and writes are refused.
  - App's restore effect waits until the user is known and re-runs when the user changes.
- **Reading positions:**
  - Keys become `neural-pdf-progress@<ownerId>/<fileName>`.
  - Legacy `neural-pdf-progress-<fileName>` keys are moved to the claiming user.
  - With no owner, nothing is saved or restored.

**Tests:**
- Two users on one browser: each sees only their own chats, workspace and positions.
- Legacy data of each kind is claimed once.
- With no owner, all three are empty and writes are refused.
- The workspace restore does not run before the user is known.

### Task B: Read-aloud never plays the previous page's audio

**Why:** A TTS fetch still in flight when `clearCache` runs (a page turn, a new document, a citation jump) stores its clip in the *new* page's cache at the same index. So the new page can play a sentence from the old one (v2.1 Task 7 deferred minor).

**Change:**
- `useTtsEngine` keeps a cache generation. `clearCache` bumps it.
- A fetch that finishes under an older generation revokes its URL and caches nothing.

**Test:** a fetch started before `clearCache` and finished after it leaves the cache empty and revokes its URL.

### Task C: The open document's id is always its own bytes' hash

**Why:** Two cases, both from the v2.1 final re-review:
1. **Stale cache entry:** `docHash`'s cache is keyed by name. A hash still in flight for load N can refill the cache after load N+1 has called `forgetDocHash`, when both files are the same size.
2. **Workspace files:** a file opened from a workspace folder is not saved to the local library. `ensureDocHash` then reads a *same-named library book* and uses that book's id for Index and chat.

**Change:**
- `getOrComputeDocHash` caches a result only if its name wasn't forgotten while hashing (a per-name generation).
- `usePdfEngine` exposes whether the open document is in the local library. `ensureDocHash` returns null for a workspace file, where it would otherwise read a same-named book. That is the same outcome as today for a workspace file with no same-named book.

**Tests:**
- A hash finishing after a forget isn't cached.
- A workspace-opened file whose name matches a library book gets no doc id.
